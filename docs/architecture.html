DrLabs Framework: 구조와 워크플로우

여러 제조사의 모터를 하나의 API로 다루는 순수 Rust 모터 제어 프레임워크입니다. 로봇은 JSON 설명서 한 장과 실행 파일 하나입니다. 이 페이지는 현재 구현된 것을 계층, 데이터 흐름, 실행 경로, 작업 순서, 검증 상태 순으로 보여줍니다.

3. 두 실행 경로 — Session과 rt

같은 core, 같은 드라이버 위에 실행 경로가 둘 있습니다. 하나는 축 하나를 사람이 또는 상위 프로그램이 다루는 Session 경로, 다른 하나는 기계 전체를 고정 주기로 도는 rt 런타임입니다. 2026-10-27부터 다관절은 rt가 맡고, Session 경로는 단일 축 도구용으로 남아 있습니다.

5. 안전 — 두 층, 그리고 Fault 래치

상태와 동사는 CiA 402 이름을 씁니다. switched on(토크 off) → operation enabled(토크 on), 트립이나 quick stop이면 fault, fault_reset으로만 풀리고 풀려도 switched on입니다. 2026-11-02에 "armed" 어휘를 전부 이것으로 바꿨습니다.

테스트가 잡도록 만들어진 것

  • 와이어가 움직이지 않았다. moteus 프레임 11종을 공식 Python 패키지 출력과 바이트 단위로 고정. 실패하면 인코더가 바뀐 것이고, 기대값을 고치는 쪽이 아니라 참조 구현에서 다시 뽑습니다.
  • 레이트 실링. 600 ms 동안 명령을 쏟아부어도 루프가 설정 rate 근처에 머무는지 단언. 실링을 빼면 50 Hz 설정에서 520 564 Hz가 나와, 테스트가 그 결함을 잡는다는 것 자체가 확인됨.
  • 찢김 없음. 트리플 버퍼가 항상 온전한 레코드를 건네는지. no_alloc 테스트는 Guard와 시뮬 틱 경로에 할당이 없는지 봅니다.
  • 토크 방향. 기어비로 나누는 쪽을 전용 테스트로 고정.
  • macOS 수면 정확도. time-constraint 정책 아래 15–50 µs 안에 깨어나는지. 하이퍼바이저 게스트(CI)에서는 건너뜀.

시뮬이 말해주지 못하는 것

기구에 대한 모든 것. 실제 축이 못 가는 목표에, 실제 모터가 거부할 토크로 기꺼이 도달합니다. 그래서 하드웨어에서 찾은 결함은 전부 "돌아가는 소프트웨어처럼 보였던" 것이었습니다. operation enabled 뒤 첫 명령을 거부한 서보, 성공을 보고하며 67 Hz로 돌던 루프, 엉뚱한 키에서 읽힌 설정값.

8. 타임라인 — 어떻게 여기까지 왔는가

9. 아직 안 된 것

  • Linux 실행. SCHED_FIFO · mlockall · 코어 고정은 타입체크만 됐고 로봇 PC에서 돌린 적이 없습니다. 500 Hz 운용의 기준 숫자는 거기서 나와야 합니다.
  • rt 경로에 실기 버스. rt 런타임은 시뮬 버스로만 돌았습니다. moteus는 Bus 트레이트 구현이 없어 rt에서 못 씁니다.
  • macOS 실기. IOSSIOSPEED 경로와 Apple FTDI 드라이버의 레이턴시 타이머(16 ms 추정)는 문서 기준 구현입니다. 체크리스트는 DYNAMIXEL.md macOS 절에 있습니다.
  • RobStride와 ODrive 실기. 둘 다 벤치에 올라온 적이 없습니다.
  • 공유 버스에 두 컨트롤러. Session 경로의 잠금은 구조상 맞지만 실제 어댑터로 두 컨트롤러를 돌린 적이 없습니다.
  • 와이어 예산 검증. rt -check는 축 수와 rate만 보고, 버스별 틱당 바이트가 period에 드는지는 보지 않습니다. Dynamixel 500 Hz는 4 Mbps 버스당 8축이 안전값, Fast Sync Read 확인 시 12–13축입니다.
  • CLAUDE.md. 아직 Go 레이아웃을 설명하고 있어 현재 Rust 워크스페이스와 맞지 않습니다.
  • ROS 2 실기 검증. 2026-11-03에 rt 와이어를 UDP에서 CycloneDDS(ROS 2 명명, drlabs_msgs)로 바꾸고 Rust·Python 클라이언트와 시뮬에서 확인했지만, 실제 ROS 2 노드(rmw_cyclonedds)로 구독한 적은 아직 없습니다.
